\section{Data, Simulated Samples, and Software Versions}
\label{sec:data}

\subsection{Data samples}
\label{sec:data:data}

The analysis uses Proc16 and Prompt16 data, covering both Run~1 and Run~2, and
is evaluated separately for the $e$ and $\mu$ channels throughout.
The run periods are kept separate rather than merged from the outset because
several inputs are run dependent: the PID correction tables
(Sec.~\ref{sec:corrections:recommended}), the fake-$D$ normalisation, and the
generic-$B\bar{B}$ weights themselves (Sec.~\ref{sec:bbbar:rundep}).
Where a combined result is wanted, the run periods are corrected separately
and only then concatenated, so that the run dependence survives the
combination.

Both on-resonance ($\Upsilon(4S)$) and off-resonance samples are processed.
The off-resonance sample contains no $B\bar{B}$ events and is therefore the
only control sample in which the continuum background can be studied without a
$B\bar{B}$ component to subtract (Sec.~\ref{sec:validation}).
The wrong-charge reconstruction is run only for on-resonance input
(Sec.~\ref{sec:recon:wc}), so the off-resonance sample has no wrong-charge
counterpart.

\subsection{Simulated samples}
\label{sec:data:mc}

Simulation is the MC16rd campaign, of two distinct kinds that are not
interchangeable.

\emph{Generic MC} decays particles according to their measured branching
fractions, so that it simulates real data as a whole; it is produced at four
times the data luminosity, so a factor of $0.25$ is applied whenever an
absolute normalisation is compared with data
(\texttt{CODE\_FACT}: \texttt{LUMINOSITY\_SCALE = \{"all\_mc": 0.25\}} in
\texttt{Old\_scripts/}; the current notebooks apply the same $0.25$ literal
per call rather than through that shared constant).

\emph{Signal-enriched MC} instead forces the decay of interest and is
produced mode by mode with a large number of events (of order $3\times10^{7}$
for a single mode), which supports the detailed studies that require high
statistics but cannot itself be compared directly to data, since it contains
no real background events.
Three signal-enriched samples are used in this analysis, all producing the
charged-$D$ final state used in the signal reconstruction, though not all
from a $B^{0}\bar{B}^{0}$ event: the $D$ and $D^{*}$ samples are generated
as $B^{0}\bar{B}^{0}$ only, while the $D^{**}$ sample is generated as both
$B^{0}\bar{B}^{0}$ and $B^{+}B^{-}$, as its four additional modes require:
\begin{itemize}
  \item one $B \to D\tau\nu$ mode (neutral $B$, charged $D$);
  \item one $B \to D^{*}\tau\nu$ mode (neutral $B$, charged $D^{*}$; the
        neutral $D^{*}$ does not decay to a charged $D$ and so does not
        contribute to this final state);
  \item eight $B \to D^{**}\tau\nu$ modes: four with a neutral $B$ and a
        charged $D^{**}$, and four with a charged $B$ and a neutral
        $D^{**}$, since both charge combinations of $D^{**}$ decay to a
        charged $D$.
\end{itemize}
These three signal-enriched samples feed the $Pyhf$ fit templates of
Sec.~\ref{sec:fit:templates}; in addition, the $B\to D\tau\nu$ sample supplies
the signal class of the BDT training (Sec.~\ref{sec:mva:classes}).
\AnalysisTBD{production identifiers and generated event counts for the three

At the current development stage, generic MC is used for every study except
the BDT training, where both generic MC (the three background classes) and
signal-enriched MC (the signal class) are used (Sec.~\ref{sec:mva:classes}).
Signal-enriched MC is needed only for the sensitivity estimate and the final
$Pyhf$ fit (Sec.~\ref{sec:fit}, Sec.~\ref{sec:results}), so the generic-MC
factor of $0.25$ is the one that appears in most data/MC agreement checks at
this stage.
When a signal-enriched sample is used to build a fit template, its scale
factor is derived rather than fixed at $0.25$: if a sample of $B$ generated
events, after reconstruction and truth-based selection of correctly
reconstructed candidates (Sec.~\ref{sec:truth}), gives $B$ correctly
reconstructed events, and the same mode has $A$ correctly reconstructed
events in generic MC, the signal-enriched sample's effective scale factor is
$0.25 \times A / B$ --- i.e.\ it is normalised to reproduce the same
correctly reconstructed yield that the (lower-statistics) generic MC would
give at the data luminosity.

\subsection{Software versions}
\label{sec:data:software}

Three release names appear in the analysis chain and they play different
roles, so they are distinguished here explicitly.

Data and simulation are produced and processed with the basf2 \emph{main}
release \texttt{release-08-00-08}.
The main release contains all basf2 packages and is what is used for data
taking, MC production and data processing.

The analysis-level reconstruction of Sec.~\ref{sec:reconstruction} is run with
the basf2 \emph{light} release \texttt{light-2505-deimos}, a subset of the main
release containing the packages needed for physics analysis.
This is the nominal analysis release for this note.
The next major production update is expected to use
\texttt{light-2607-kasei}.

Release names appearing inside global-tag names --- for example
\texttt{pid\_nn\_release08\_v1} and
\texttt{tracking\_release08\_20260119\_EnergyMomentumScale} --- refer to the
release used when those payloads were prepared.
They are not the release used for this analysis and should not be read as such.

Global tags used are the analysis global tag returned by
\texttt{getAnalysisGlobaltag()}, \texttt{pid\_nn\_release08\_v1} for the
neural-network identifiers, and
\texttt{tracking\_release08\_20260119\_EnergyMomentumScale} for the track
momentum-scale and energy-loss payloads.

\subsection{Ntuple production and offline samples}
\label{sec:data:ntuples}

The steering script writes four trees per input sample: \texttt{B0\_e} and
\texttt{B0\_mu} for the nominal reconstruction, and \texttt{B0\_wc\_e} and
\texttt{B0\_wc\_mu} for the wrong-charge sample, the latter two only for
on-resonance input.

Offline, the grid output is combined per run period and channel into files of
the form \texttt{4S\_<period>\_deimos\_BDT\_<channel>\_3.root}, containing the
trees \texttt{MC\_<channel>\_comb} and \texttt{Data\_<channel>\_comb}.
These are the files consumed by the generic-$B\bar{B}$ tuning and by the
plotting notebooks.
That combination step also applies the classifier of Sec.~\ref{sec:mva} and
constructs \texttt{p\_D\_l}, one of the two fit observables.

\subsection{Event weights and normalisation}
\label{sec:data:weights}

Every weighted MC histogram in the analysis is filled with the product of up to
four per-event columns: a base weight \texttt{\_\_weight\_\_}, the PID
correction weight, the generic-$B\bar{B}$ category weight, and a run-dependent
factor used when run periods are combined.
The luminosity factor of Sec.~\ref{sec:data:mc} multiplies the product.
Each column is included only if it is present in the frame, so a missing
column is silently treated as unity rather than raising.

\InProgress{\texttt{\_\_weight\_\_} is being retired as a name: it has been
reused for several unrelated purposes across the analysis history (including
the class-balancing role in \texttt{Old\_scripts/}), and a single generically
named column that means different things in different contexts is exactly
the kind of silent ambiguity Sec.~\ref{sec:corrections:order} warns about.
The intended replacement is one distinctly named column per correction, so
that a column's name states what it contains rather than requiring the
reader to know which chain produced it.  This has not yet been implemented in
\texttt{utilities.py}}

\subsection{Sample overlap}
\label{sec:data:overlap}

At the current development stage, generic MC is used for template building
and for three of the four BDT training classes (\texttt{bkg\_fakeD},
\texttt{bkg\_continuum}, \texttt{bkg\_combinatorial}); the fourth,
signal-like training class alone is drawn from the $B \to D\tau\nu$
signal-enriched sample (Sec.~\ref{sec:data:mc}, Sec.~\ref{sec:mva:classes}).
For the signal-enriched sample specifically, the fit templates are currently
also built from generic MC (not from that sample), so it does not yet
overlap with the template-building input.

The three generic-MC training classes are a different matter, and here an
overlap already exists now, not only after the transition described below.
\texttt{Notebooks/2\_create\_BDTtrainingSet.ipynb} draws its
\texttt{bkg\_fakeD}/\texttt{bkg\_continuum}/\texttt{bkg\_combinatorial}
training events from a \emph{Run~1-only} generic-MC production
(\texttt{4S\_run1\_deimos\_1}, $e$ channel), while
\texttt{Notebooks/3\_fitting\_cabinetry\_2d\_SR.ipynb} builds the fit
templates from the corresponding BDT-scored files of \emph{both} run periods,
\texttt{4S\_run1\_deimos\_BDT\_\textless channel\textgreater\_3.root} and
\texttt{4S\_run2\_deimos\_BDT\_\textless channel\textgreater\_3.root}
combined (Sec.~\ref{sec:data:ntuples}).
Taking the per-class reconstructed sample sizes of
Sec.~\ref{sec:truth:composition} (which are themselves Run~1-only, as noted
there) and the $500\,000$-event training subsample of
Sec.~\ref{sec:mva:classes} at face value, this puts roughly
$500\,000/15\,815\,120 \approx 3\%$ of the Run~1 reconstructed
\texttt{bkg\_fakeD} pool, but roughly $500\,000/734\,906 \approx 68\%$ of
Run~1 \texttt{bkg\_continuum} and $500\,000/739\,879 \approx 68\%$ of Run~1
\texttt{bkg\_combinatorial}, into the BDT training set.
Because these percentages use the Run~1-only reconstructed pool as the
denominator while the fit templates for these two classes are built from the
larger Run~1$+$Run~2 combined pool, the fraction of the \emph{full}
template-building pool that was also used for training is smaller than the
$68\%$ quoted above; no Run~2 (or combined) equivalent of the reconstructed
\texttt{bkg\_continuum}/\texttt{bkg\_combinatorial} counts is currently
computed or stored anywhere in the repository, so the true fraction cannot
yet be stated.
\AnalysisTBD{obtain the Run~2 (and combined Run~1$+$Run~2) reconstructed
event counts for \texttt{bkg\_continuum} and \texttt{bkg\_combinatorial}, to
state the true overlap fraction against the actual template-building pool
rather than the Run~1-only approximation above}

Since the same classifier that was partly trained to recognise those events
as continuum/combinatorial is then applied to select and shape their own fit
templates, this in-sample evaluation could in principle make the
post-selection shape or purity look better than it would generalise to
independent events.
Per the analyst, however, this is not necessarily concerning even at full
overlap: if the classifier's inputs and output are only weakly correlated
with the two fit observables ($\mmiss$ and $\pdl$) within a given truth
category, then selecting on the classifier does not sculpt the fit-variable
shape, regardless of whether the selected events were also used to train the
classifier.
This is a plausible mitigating argument, not yet a demonstrated one: it is
exactly the quantity Appendix~\ref{app:mva:todo}'s classifier-diagnostics
item calls for (the correlation of each retained input with $\mmiss$ and
$\pdl$ in the fit bins), which has not yet been produced.
\AnalysisTBD{quantify whether the in-sample evaluation measurably biases the
\texttt{bkg\_continuum}/\texttt{bkg\_combinatorial} template shapes or
efficiencies (for example by comparing templates built only from the
held-out $20\%$ validation split of Sec.~\ref{sec:mva:training} against the
current ones, and by the input/fit-observable correlation study of
Appendix~\ref{app:mva:todo}), and, if a bias is found, enforce a disjoint
split between the events used for BDT training and the events used for
template building for these two classes.
This is a currently active risk, not only a concern for the future
signal-enriched-template transition below}

That transition is a related but separate case: once signal-enriched MC is
used to build the signal and normalisation templates for the final fit, as
intended (Sec.~\ref{sec:data:mc}), the same $B \to D\tau\nu$ sample would
then supply both the signal class of the BDT training and its own fit
template, and the disjoint train/validation split used within the training
sample (Sec.~\ref{sec:mva:training}) does not by itself establish that the
template is independent of the classifier that selects it.
\AnalysisTBD{state and enforce an explicit rule preventing overlap between

code that split is made}
